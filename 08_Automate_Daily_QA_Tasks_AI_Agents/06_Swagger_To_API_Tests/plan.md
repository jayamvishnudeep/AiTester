# Plan — Swagger to API Tests (n8n AI Agent)

An API QA points this at an OpenAPI spec and gets back a runnable test
collection: a happy path for every operation, plus the negative tests the spec
already implies — missing required parameters, wrong types, invalid enums, and
calls made without credentials.

Status: **built and tested against the live Groq API.** Fifty-four assertions
pass, including a real model call. Not yet imported into n8n Cloud.

## The brief

| | |
|---|---|
| Audience | API QA |
| Problem | Low API test coverage |
| Input | OpenAPI / Swagger spec |
| Output | Ready-to-run Postman / RestAssured tests |
| Helpful for | Quickly bootstrapping API testing coverage |
| Given shape | Webhook → HTTP Request (fetch spec) → AI Agent (test generator) → Code (format collection) → File output |

## The rule this one is built on

Every agent in this folder has a line between what code decides and what the
model decides. Here that line is unusually sharp:

> **Everything the spec determines is generated by code. The model only adds
> what a schema cannot imply.**

A test derived from the spec is *correct by construction*: if the document says
`GET /pets/{petId}` takes a required integer path parameter and returns 200 or
404, then a test that omits it and expects a 4xx is right without anyone
checking. A model-invented endpoint is a test that 404s on first run and gets
deleted — along with the rest of the suite's credibility.

This also fixes the coverage problem for free. The deterministic tests are
generated for **every** operation in the spec, however large it is, because
generating them costs no tokens. Only the edge-case pass is budgeted. Coverage
therefore does not degrade with spec size, which is the opposite of what happens
if the whole job is handed to a model.

## What code generates, per operation

Straight from the document, no model involved:

| Test | Derived from | Expects |
|---|---|---|
| Happy path | path, method, example/default/enum values | the documented 2xx |
| Missing required parameter | `required: true` on each param | 4xx |
| Wrong parameter type | `type` on each typed param | 4xx |
| Invalid enum value | `enum` on a param | 4xx |
| Missing request body | `requestBody.required` | 4xx |
| No credentials | `security` / `securitySchemes` | 401 or 403 |

Every one of those assertions is made against **codes the spec actually
documents**, not against a generic 4xx: the expected list is taken from the
operation's `responses` map, falling back to sensible defaults only when the
document is silent. So each test doubles as a check that the API and its
documentation still agree — which is the cause of "low API test coverage" at
least as often as nobody having written tests.

## What the model adds

Only for operations the parser found, and only things a schema cannot state:

```
scenarios[]      { name, method, path, why, steps[], test_data, expect, priority }
sequence_notes   what must run before what, and what is carried between calls
data_notes       what must exist before the suite can run at all
gaps[]           coverage the specification makes impossible
```

`method` and `path` are the fields that make the guard rail possible: they are
checked against the parsed operations, so a scenario cannot name an endpoint
that does not exist.

"Create a pet with a 300-character name" is a boundary a schema implies.
"Create an order, then cancel it, then try to cancel it again" is not — and that
is the kind of test worth a model call.

## The failure mode

**A model asked to write tests from a spec will produce plausible tests for
endpoints that do not exist.** Invented paths, parameters that were never
declared, auth headers the API does not use. They look like a comprehensive
suite, they fail on the first run, and the team concludes the tool is useless.

So every model-contributed test is checked against the parsed spec: the
`path` + `method` must exist, and every parameter it names must be declared on
that operation. Anything else is dropped and counted. That is the same shape as
the quoted-line check in `02_` and the figure check in `03_`.

## Two things the input will fight

**`$ref` is everywhere.** The real Swagger Petstore spec uses `$ref` 43 times.
Without resolving them, a request body is `{"$ref": "#/components/schemas/Pet"}`
and no example can be built from it. The parser resolves local
`#/components/...` references, with a depth cap so a self-referential schema
cannot hang the node.

**Most specs in the wild are YAML, and a Code node has no YAML parser.** v1
accepts **JSON only** and says so clearly when handed YAML, rather than failing
obscurely. That is less limiting than it sounds — Spring Boot serves
`/v3/api-docs` as JSON, FastAPI serves `/openapi.json`, and `swagger-cli bundle`
converts a YAML file in one command. Writing a YAML parser by hand to avoid
saying "convert it first" would be the wrong trade.

## The pipeline

```
Webhook            POST /swagger-tests  { spec_url | spec, base_url, auth, max_operations }
  -> Fetch Spec        (HTTP Request)  when a URL was given
  -> Parse Spec        (Code)  resolve $refs, enumerate operations,
                               generate every deterministic test
  -> API Test Designer (AI Agent + Groq + Structured Output Parser)
  -> Build Collection  (Code)  verify the model's tests against the spec,
                               assemble the collection
  -> Convert to File   -> Send to Telegram -> Respond to Caller
```

The Code node before the agent is what makes this work: the model receives a
compact summary of operations, never the spec itself, so a 6 MB document does
not have to fit in a context window.

## Decisions taken

**1. Both formats.** A Postman v2.1 collection, whose structure is validated in
code before it is handed over, and a RestAssured JUnit class for a team that
already has a Maven project. Both are generated from the same test list, so they
cannot drift.

**2. Response, plus Telegram.** The webhook returns everything — the collection
JSON, the Java source, the scenarios and the gaps. Telegram gets a readable
summary and the collection as an attachment, so it arrives somewhere usable
without anyone running a curl command.

## What was found by building it

**A `$ref` depth cap has to count hops, not nesting — and getting that wrong
fails silently.** The first version capped the resolver on structural recursion
depth. It looked correct on a shallow schema and produced this for the request
body:

```
{"customerId": 4471, "items": ["string"], ...}
```

`items` should be `[{"sku": "SKU-4471", "quantity": 2}]`. The `$ref` to
`OrderItem` sits a few levels down inside the array, and by the time the walker
reached it the depth budget was spent — so it was left as `{"$ref": ...}`, an
object with no `type`, and the example builder fell through to the string
`"string"`. No error, no warning, just a body example that would fail every
POST test.

Real specs are deeply nested, so this would have degraded on almost all of them
while passing on the sample. Only a reference *cycle* can recurse forever, so
hops are the right thing to cap: the recursion guard still stops a
self-referential schema at six hops.

**The deterministic pass is worth more than expected.** Five operations produce
**19 tests** with no model involvement: 5 happy paths, 3 missing-required, 4
wrong-type, 2 invalid-enum, 1 missing-body, 4 unauthenticated. That ratio holds
for any spec, and none of it is subject to a token budget.

## Test result

Both Code nodes are executed with mocked n8n globals and one real Groq call is
made with the real system message. **Fifty-four assertions, all passing.**

The parser resolves `$ref` through an array into a nested schema, honours
`security: []` on a single operation while inheriting root security elsewhere,
prefers a spec `example` over a `default` over an invented value, refuses YAML
with a message naming the fix, and survives a self-referential schema.

The Postman output is checked as an artefact rather than as text: it parses,
declares the v2.1 schema, carries one request per test plus the scenarios, uses
`{{baseUrl}}` and `{{authToken}}` variables rather than hardcoding, substitutes
path parameters into the URL (`{{baseUrl}}/orders/90210`), and the
unauthenticated test carries no `Authorization` header. The Java output has
balanced braces, unique method names, one `@Test` per generated test, and reads
its base URL from a system property.

**The live call** cost 4,213 tokens in 5.7 seconds and produced scenarios that
are genuinely outside what the schema states:

```
[High]   DELETE /orders/{orderId}  Cancel an already-cancelled order
         why: ensures the API is idempotent and returns a conflict
[High]   GET /orders/{orderId}     Fetch order after cancellation shows cancelled status
[Medium] GET /orders               status=cancelled returns only cancelled orders
[Medium] GET /orders               limit truncates without padding
```

with nothing rejected, and gaps worth sending to the API owner: no endpoint
exists to move an order from `placed` to `packed` or `shipped`, so
state-dependent behaviour cannot be tested at all, and no pagination cursor is
documented.

The guard rail was tested by attacking it: a scenario for
`POST /orders/{orderId}/refund` is dropped and named in `scenarios_rejected`,
and a `PATCH` on an operation that only supports `GET` and `DELETE` is dropped
too.

## Deliberately not in v1

- **No test execution.** This writes the suite; running it is `newman`'s job.
- **No response-schema assertions beyond status codes.** Validating a response
  body against its schema is worth doing and is a bigger piece of work than the
  rest of this put together.
- **No spec diffing.** "What changed since the last version, and which tests
  need updating" is the natural v2 and needs somewhere to keep the last spec.
